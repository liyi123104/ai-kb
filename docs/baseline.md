## 3. 判定口径（写清楚，避免以后自欺）

- **召回命中**：Top-5 中存在一条，文件名等于 `expected_source`，且 `expected_page` 落在该条的
  `[page_start, page_end]` 区间内。页码是 PDF 物理页。
- **答案正确**：用 `qwen2.5:7b` 做语义评审（允许跨语言、允许改写，关键事实一致即算对），
  再人工抽检 4 条确认评审没有乱判。计划书原话是「人工标注」，本项目用「模型评审 + 人工抽检」
  替代，这一点在 T4 的结果里有记录，不冒充纯人工。
- **首字延迟**：流式接口从发出请求到第一个 token 到达的时间（模型已加载的热态）。

## 6. 已知问题与处置

| 问题 | 处置 |
|---|---|
| Ollama 版 bge-m3 对个别 token 返回 500 `NaN`（实测 `sequence.` 触发） | 在 `app/llm.py` 的 `SafeOllamaEmbeddings` 里加降级：失败则逐个重试并从尾部逐词缩短（最多砍 1/3），保证检索不整体失败 |
| 目录页 / 参考文献页污染检索 | 切片生成时剔除参考文献类；检索时过滤目录点线与二进制碎片 |
| 7B 模型过度拒答（明明能答却先写「资料中没有」） | 改 prompt：只有确实找不到依据时才允许那句话，并要求第一行直接给答案 |
| 生成被无关上下文带偏 | 生成只用 Top-3（检索指标仍按 Top-5 统计） |
| 首字延迟临界 3 秒 | 冷启动 8.8s、热态 2.7–3.2s；后续在 T3.4/T5 里观察，必要时预热模型 |

## 6.5 上下文条数的影响（2026/10/20 补测）

| 喂给模型的上下文条数 | 召回率 | 答案准确率 |
|---|---|---|
| 1 条 | 90.0% | 70.0% |
| **2 条** | **90.0%** | **83.3%** |
| 3 条 | 90.0% | 76.7% |

3 条时反而比 2 条差：多出来的第 3 条往往是"相关性一般"的片段，会把 7B 模型带偏。
默认已改为 2 条（`ANSWER_TOP_N=2`），可用环境变量覆盖。

## 8. 实际服务延迟（2026/10/20 补测，含前端链路）

计划书 F5 要求「首字 ≤3 秒、完整 ≤15 秒」。在**真实服务链路**（浏览器 → Vite 代理 → FastAPI → Ollama）
上复测，结果与第 2 节的早期测量有差距，如实记录：

| 场景 | 首字 | 整轮 |
|---|---|---|
| 冷启动首次请求（模型需加载） | 10–20 秒 | 15–25 秒 |
| 模型常驻、热态（最佳情况） | 3.2 秒 | 6.5–10 秒 |
| 模型被卸载后（隔几分钟再问） | 5.6–6.9 秒 | 8.7–11.5 秒 |

**原因（逐条实测定位）**：

1. **6GB 显存放不下两个模型**：qwen2.5:7b 占 4.4GB、bge-m3 占 1.2GB，同时驻留会挤爆显存，
   生成速度明显下降；
2. **LangChain 的 embeddings 没有把 `keep_alive` 传给 Ollama**，bge-m3 在两次请求之间被卸载，
   每次检索都要重新加载 2.2 秒 —— 已改为直连 `/api/embed` 并显式下发 `keep_alive`；
3. **Ollama 的 prompt 缓存会被无关调用冲掉**：早期保活线程用 `llm.invoke("ping")` 每 4 分钟
   打一次，导致下一次真实请求要重新做 prompt 求值（首 token 从 0.5s 掉到 3.5s）—— 已改成
   `num_predict=0` 的空 generate 调用。

**已实施的优化**（都在代码里，不是纸面方案）：`keep_alive=30m`、启动预热 + 4 分钟保活、
向量库客户端单例（省 0.8s/次）、`num_ctx=2048`（KV 缓存减半，整轮 5.3s → 2.9s）、
向量模型放 CPU（`num_gpu=0`，给生成模型腾 1.2GB 显存）。

**结论：首字 ≤3 秒在本机（6GB 显存 + 7B 本地模型）达不到，最好情况 3.2 秒、常见 5–7 秒。**
两条可行路线：
- 演示/录视频时把 `LLM_PROVIDER` 切成 `deepseek`（云端，首字通常 1–2 秒，需 API Key）；
- 或换更小的生成模型（如 qwen2.5:3b），但那属于换技术选型，需要先确认。
