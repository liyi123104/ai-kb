## 三、问题清单

### P0 · 语料领域漂移

28 个文件里只有 26% 与「AI 学习资料」相关；PostgreSQL 手册（15,669 片）、Adobe PDF 规范（5,499 片）等占了 74%。检索耗时因此从 0.4 秒涨到 0.92 秒，产品定位也从「AI 学习知识库」变成了「混合技术库」。

**建议**：按领域拆集合（ai-kb / tech-ref），检索时指定集合；或移除与目标无关的大部头。

### P0 · 没有任何鉴权

/files、/upload、DELETE /files 全部无需凭证即可调用（实测 HTTP 200）。本机自用没问题，一旦按 T6.2 部署到公网，任何人都能上传或删除你的资料。

**建议**：加一个简单 token（请求头 X-Token 比对 .env），或部署侧用 Nginx basic auth。

### P1 · 质量指标粒度太粗

30 题里每题值 3.3 个百分点：本次 73.3% 与上次 76.7% 其实只差 1 道题，在没有多次采样的情况下无法判断是退化还是噪声。

**建议**：固定测试集跑 3 次取均值；或扩充到 100 题；并人工抽检 10 题校准 LLM 判定。

### P1 · 入库吞吐受外部因素支配

同一份文件在不同时刻相差 20 倍以上（2 片/秒 vs 55 片/秒）。实测两次是因为同机另一个项目在调 Ollama，把 bge-m3 挤出显存。

**建议**：1) 入库前检测 /api/ps，发现别的模型占用就提示；2) 或用独立端口跑第二个 Ollama 实例；3) 或加任务队列串行化，避免两个上传互相抢显存。

### P1 · 上传任务状态不持久

任务表 _UPLOAD_JOBS 在进程内存里：服务重启后，正在入库的文件状态丢失，前端轮询会拿到 404，用户不知道到底成没成。

**建议**：把任务状态写进 SQLite（一行一个任务），重启后可查历史；或启动时扫描 uploads 目录补登记。

### P1 · 检索缺精排

Top-1 命中 19/30，平均名次 1.48：有 11 道题正确片段不在第一位。计划书的 E2（bge-reranker）一直未做。

**建议**：对 Top-5 跑一次 rerank 再取前 2 条喂模型；代价是每次多 50–150 毫秒。

### P2 · 前端没有「停止生成」

streamChat 已支持 AbortSignal，但界面上没有取消按钮，长回答只能等。

**建议**：输入框旁加一个停止按钮，调用 abort()。

### P2 · 日志只有 stdout

7 处 print 代替日志，无请求 ID、无轮转；容器里只能 docker logs 翻。

**建议**：换 logging + 文件轮转，关键路径带 request_id。

### P2 · 文件列表无分页

28 个文件尚可，上百个会很长；每次刷新拉全量元数据。

**建议**：加分页或虚拟滚动。

### P2 · Docker 内生成慢 2–4 倍

容器内问答 13–22 秒，本机 3–6 秒；原因是 Docker Desktop 的 WSL2 与宿主抢 CPU。

**建议**：真实 Linux 服务器上不明显；若要在 Windows 上演示，录屏用本机模式。

## 五、改进路线

### 立刻（半天内）

- 给接口加 token 鉴权（改动小，堵住最大的安全洞）
- 把语料按领域拆成两个集合，问答时指定集合

### 短期（1–2 天）

- 评测跑 3 次取均值，并把结果写进基线文档
- 上传任务状态落 SQLite，重启可恢复
- 前端加「停止生成」按钮

### 中期（1 周）

- 接 bge-reranker 做精排（计划书 E2），观察 Top-1 命中率
- logging 改造 + 请求 ID
- 补 3 类测试：并发上传、Ollama 宕机、浏览器端到端


## 六、值得肯定的地方

- 关键结论都有实验支撑（E1/E4/E5/E6/E7/E8），参数不是拍脑袋定的。
- 踩过的坑都留了记录且修掉：IPv6 回退、langchain 丢 keep_alive、保活覆盖 prompt 缓存、高亮坏缓存、SQLite 变量上限。
- 安全底线守住：.env 不入库、路径穿越防护、上传白名单与大小限制。
- 可交付性完整：一键启动、Docker 编排、四份技术文档、简历与视频脚本。
